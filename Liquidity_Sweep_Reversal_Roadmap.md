# Liquidity Sweep Reversal — Implementation & Research Roadmap

**Document name:** `Liquidity_Sweep_Reversal_Roadmap.md`  
**Status:** FINAL — implementation-ready specification  
**Baseline symbol:** XAUUSD  
**Baseline signal timeframe:** M1  
**Research risk default:** 0.50% per trade = 1R  
**Default Daily Loss Guard:** ON, 3R  
**Default Max Concurrent Positions:** 3  
**Default Daily Profit Target:** OFF, configurable to 9R  

---

## 0. Non-Negotiable Architecture Rules

These rules apply to every phase and are not optional implementation details.

1. **Broker Server Time is the source of truth.** No manual UTC/DST conversion is used for strategy session logic. FundedNext server time changes with its own DST handling; the EA reads broker/server timestamps directly.
2. **Signal timeframe is an input.** Default `M1`; later the same engine must support `M5`, `M15`, `M30`, `H1`, etc. Signal logic must not be hard-coded to M1.
3. **Execution is tick-based.** Entry, SL/TP triggering, spread, commission and other execution effects use the actual tester tick/quote data. The research engine is intended for **Every tick based on real ticks**.
4. **No average/bar spread for execution.** The engine must read the actual Bid/Ask from the exact tick used by the event. `Ask-Bid` at that moment is the spread used for that event.
5. **No look-ahead.** A swing or higher-timeframe structure element is usable only after all candles needed to confirm it have closed.
6. **No hidden rules.** Entry, SL, TP, BE, re-entry, risk admission, session behavior, and report calculations must each have explicit deterministic rules.
7. **Research and reporting are separate from strategy detection.** A single market pass creates a trade/event ledger; reports are generated by grouping/aggregating that ledger, not by rerunning the backtest per month/year.
8. **2025 is permanently reserved for OOS in the extended test.** It must not be used for rule selection, parameter tuning, filter approval, or optimization before the OOS run is frozen.
9. **Every phase that changes code must update this roadmap file.** The roadmap filename and relative path must never change.
10. **Every completed phase must output a patch package containing the updated roadmap plus every new/modified file using the original filenames and relative paths. Unmodified files are untouched.**

# Phase 1 — Research Engine Foundation: Data, Time, Sessions, Costs & Risk Model

### Goal
Build the deterministic research foundation before strategy-specific signal logic is added.

### Scope

#### 1.1 Signal timeframe
- Input: `SignalTimeframe`
- Default: `M1`
- Supported selectable timeframes must include at least `M1/M5/M15/M30/H1`.
- All candle-based strategy calculations use the selected timeframe.
- Tick-level execution remains independent of the selected signal timeframe.

#### 1.2 Broker/server time
- Input/group: broker/server time mode.
- Strategy session boundaries use broker time directly.
- No hard-coded UTC offset.
- No manual seasonal DST table.

#### 1.3 Trading-session modes
Input: `TradingSessionMode`

**Mode 1 — Full Day Except Late Spread Window (default)**
- New entries allowed from the first tradable tick after market open.
- New entries blocked from `21:30` through that day's market close.
- New entries resume after the next market open.

**Mode 2 — NY Window**
- New entries allowed only from `16:30` through `21:30` broker time.

**Mode 3 — Custom**
- Inputs: `TradeStartTime`, `TradeEndTime`.

Session filtering affects **new entries only**. Existing positions continue under normal trade-management rules.

#### 1.4 Spread and execution-cost model
The engine must record and use:
- Entry Bid
- Entry Ask
- Entry spread
- Exit Bid/Ask
- Exit spread
- Commission
- Swap when applicable
- Slippage/execution difference when applicable

No midpoint or averaged spread is allowed for execution calculations.

#### 1.5 Risk and R model
Input: `RiskPerTradePercent`
- Default: `0.50%`.
- 1R is dynamic and is calculated from the account-equity basis selected by the research engine at the start of each broker day.
- Position sizing/risk calculations must derive monetary 1R dynamically rather than hard-coding a cash value.

Daily loss guard inputs:
- `DailyLossGuardEnabled = true`
- `MaxDailyLossR = 3.0`

Daily profit guard inputs:
- `DailyProfitTargetEnabled = false`
- `DailyProfitTargetR = 9.0`

Position input:
- `MaxConcurrentPositions = 3`

#### 1.6 Daily risk admission
Daily loss control is a **new-risk admission guard**, not a forced floating-loss exit.

Before a new position is admitted, the engine checks:

`RealizedNetDailyR - ReservedWorstCaseOpenRiskR - NewTradeWorstCaseRiskR >= -MaxDailyLossR`

and also:

`OpenPositions < MaxConcurrentPositions`

If either condition fails, the new trade is rejected.

Examples:
- 0R realized loss + no open positions → up to 3 concurrent 1R-risk positions are possible, subject to the concurrent-position cap.
- -1R realized loss → only 2R of additional worst-case daily loss capacity remains.
- -2R realized loss → only 1R remains; only one additional 1R-risk position can be admitted.
- -3R → no new entries for the remainder of the broker day.

Floating P/L does **not** force-close an existing trade merely because daily drawdown approaches 3R. Existing trades continue to their normal exit rules.

If realized profits recover the day from its starting equity/balance reference, unused daily risk capacity may become available again, provided the risk-admission equation remains satisfied and the 3-position cap is respected.

### Required tests
- Time/session boundary tests.
- DST/server-time consistency tests.
- Exact tick spread capture tests.
- Dynamic R calculation tests.
- 3-position cap tests.
- Daily-risk admission tests with 0/1/2/3R realized losses.
- Daily profit target gating tests.

### Completion output
- Compile cleanly.
- Test logs.
- Updated roadmap with status, changed files, and a 1–2 line phase summary.
- Patch package with the updated roadmap and all changed files under their original names/paths.

# Phase 2 — Liquidity Model, Sweep Detection, Entry & Initial SL

### Goal
Implement the core Liquidity Sweep Reversal setup with no ambiguous trade rules.

## 2.1 Liquidity source types
All four are supported and individually configurable through Inputs:

1. `PreviousDayHighLow`
2. `PreviousSessionHighLow`
3. `ConfirmedSwingHighLow`
4. `EqualHighsLows`

Baseline: all four are available and enabled; each can be disabled independently for research.

### Previous Day
- Previous fully completed broker-time trading day.
- PDH/PDL are fixed after that day closes.

### Previous Session
- Previous completed liquidity session.
- Default liquidity-session definition: `16:30–21:30` broker time.
- Session start/end must remain configurable independently from the three trading-session modes.

### Confirmed swings
Default:
- `SwingLeftBars = 2`
- `SwingRightBars = 2`

A swing high/low becomes usable only after the required right-side candles have closed. No future candle data may influence an earlier signal.

### Equal highs/lows
Default tolerance:
- `EqualLevelTolerance = 3 pips`

At least two confirmed swing points within the tolerance are clustered into one equal-liquidity level.

### Liquidity clustering
If multiple sources lie within the configured clustering tolerance, they become one liquidity pool so one physical sweep cannot generate duplicate setups for the same price area.

The ledger retains all contributing source tags, e.g. `PDH + SWING + EQH`.

---

## 2.2 Exact Sweep Definition

### Buy-side liquidity sweep → Short
A valid sweep requires:

`SweepHigh > LiquidityLevel`

and, when the sweep candle closes:

`SweepClose < LiquidityLevel`

The candle must therefore take the high and close back below the level.

### Sell-side liquidity sweep → Long
A valid sweep requires:

`SweepLow < LiquidityLevel`

and:

`SweepClose > LiquidityLevel`

A wick beyond a level without a reclaim close is not a valid reversal signal.

---

## 2.3 Exact Entry

The sweep candle is the signal candle.

After the sweep candle closes, the **first valid subsequent real tick** is the execution point.

### Long
- Signal: sell-side sweep with close back above liquidity.
- Entry: market buy at the current executable `Ask` on the first valid post-close tick.

### Short
- Signal: buy-side sweep with close back below liquidity.
- Entry: market sell at the current executable `Bid` on the first valid post-close tick.

No entry at the candle close price and no midpoint execution.

---

## 2.4 Exact Initial SL

Stop is positioned beyond the sweep extreme with a fixed safety buffer:

Input:
- `SweepSLBufferPips = 3`

### Long
Reference extreme:
- `SweepLow`

Stop trigger level:
- real-price reference at `SweepLow - 3 pips`.

The stop trigger must not be allowed to occur solely because of spread expansion. The engine evaluates the appropriate real-price/reference quote and records the exact Bid/Ask and spread at the stop event.

### Short
Reference extreme:
- `SweepHigh`

Stop trigger level:
- real-price reference at `SweepHigh + 3 pips`.

Again, spread expansion by itself must not be treated as a genuine 3-pip move beyond the sweep extreme.

The actual exit execution uses the executable opposite quote (Bid for Long exit, Ask for Short exit), and all resulting spread/slippage/costs are recorded.

### Required output per setup
The ledger must retain:
- liquidity level
- source type(s)
- sweep extreme
- sweep candle time
- signal close
- actual entry quote
- spread at entry
- planned SL reference
- actual SL trigger/exit quote
- spread at exit

Same mandatory roadmap-update and patch-package rule.

# Phase 3 — Trade Management, TP/BE Matrix & Re-entry

### Goal
Implement deterministic exits, R-based reward handling, re-entry limits, and position lifecycle management.

## 3.1 TP Modes

### Mode A — Single TP (default)
Input:
- `TPMode = SINGLE`
- `TP_R = 2.0`

TP_R is fully configurable.

### Mode B — Full 15-scenario matrix
Input:
- `TPMode = FULL_MATRIX`

Run all of these scenarios in one research execution:

1. R1 / BE OFF
2. R2 / BE OFF
3. R2 / BE R1
4. R3 / BE OFF
5. R3 / BE R1
6. R3 / BE R2
7. R4 / BE OFF
8. R4 / BE R1
9. R4 / BE R2
10. R4 / BE R3
11. R5 / BE OFF
12. R5 / BE R1
13. R5 / BE R2
14. R5 / BE R3
15. R5 / BE R4

Each scenario has an independent simulated position/risk state while sharing the same single market-data pass.

---

## 3.2 Net-R-consistent TP

The selected reward is a **net research target**, not merely a raw price-distance label.

Example: for TP = 1R, a successful TP exit must produce at least the selected 1R reward after applicable modeled trading costs. Therefore the engine must solve/check the executable TP condition using actual exit-side quotes and known costs rather than declaring a TP from a raw midpoint distance alone.

For TP = 2R, successful TP must satisfy at least +2R net under the configured cost model.

Unavoidable adverse market slippage/gap beyond the intended executable level is recorded as actual execution slippage; the engine must never falsely classify a result as a full TP if the realized net result did not reach the configured target.

---

## 3.3 Break-even

`BE R1` means:
- once price reaches +1R under the scenario's executable target logic, move the stop to the actual entry price.

Likewise:
- `BE R2` triggers at +2R.
- `BE R3` triggers at +3R.
- `BE R4` triggers at +4R.

BE is never triggered at or beyond the TP.

Exit classification remains:
- `TP`
- `BE`
- `SL`
- `SESSION/NON-STRATEGY EXIT` only if a separately enabled rule explicitly causes it.

The base strategy does not close an existing trade merely because the trading session ends.

---

## 3.4 Re-entry

Input:
- `MaxAttemptsPerSetup = 1` (default)

Allowed values:
- 1 = initial entry only
- 2 = initial + 1 re-entry
- 3 = initial + 2 re-entries
- 4 = initial + 3 re-entries

A re-entry is permitted only after a **new Sweep Event** is formed on the same liquidity pool and a new reclaim close satisfies the exact entry rule.

An immediate re-entry on the same candle/event after an SL is forbidden.

Once a setup reaches TP or BE, the setup lifecycle is closed and it cannot create another attempt.

---

## 3.5 Concurrent position and risk interaction

Every new trade must pass both:
- `OpenPositions < MaxConcurrentPositions` (default 3)
- Daily risk admission equation from Phase 1.

An existing trade is never force-closed merely because the floating loss consumes part of the daily 3R threshold.

# Phase 4 — Strategy-Specific Optional Filters

### Goal
Add three research filters directly related to sweep-reversal quality. **All three are OFF by default.**

## Filter A — HTF Structure Filter
Input:
- `UseHTFStructureFilter = false`
- default HTF: `M15` when signal TF is M1

Structure is mechanically derived from confirmed 2-left/2-right swings.

Bullish structure requires a valid HH + HL sequence.
Bearish structure requires a valid LH + LL sequence.

When enabled:
- Long setups require bullish HTF structure.
- Short setups require bearish HTF structure.
- Unclear/neutral structure = no trade.

The HTF is configurable by Input and must use only information known at signal time.

## Filter B — Sweep Quality Filter
Input:
- `UseSweepQualityFilter = false`
- ATR period = 14

Default requirements:
- sweep penetration >= `0.10 × ATR(14)`
- sweep penetration <= `0.50 × ATR(14)`
- reclaim distance >= `0.10 × ATR(14)`

ATR is calculated from completed pre-sweep candles only; the sweep candle itself is excluded from the ATR calculation.

## Filter C — Opposing Liquidity / Target Room Filter
Input:
- `UseTargetRoomFilter = false`

For Long: the selected TP must lie before the nearest relevant opposing liquidity level.

For Short: the selected TP must lie before the nearest relevant opposing liquidity level in the direction of the move.

If no valid opposing liquidity is available, the trade is not rejected solely for that reason.

### Required research behavior
Each filter must be independently switchable so the same engine can test:
- all OFF
- A only
- B only
- C only
- A+B
- A+C
- B+C
- A+B+C

The filters must not alter the underlying core entry/SL rules when OFF.

### Completion output
Same mandatory roadmap-update and patch-package rule.

# Phase 5 — Backtest Engine, Scenario Runner & Reporting

### Goal
Create a single-pass research engine that can test the strategy and all 15 TP/BE scenarios without rerunning the market-data backtest for every report period.

## 5.1 One market pass
The engine reads the selected historical interval once and produces a complete event/trade ledger.

Monthly, yearly and full-period reports are generated by aggregation/grouping over that ledger.

No separate backtest is executed for January, February, March, etc.

## 5.2 Matrix-mode architecture
In Full-Matrix mode, all 15 TP/BE scenarios are simulated as independent scenario states during the same market-data pass.

Each scenario independently maintains:
- positions
- daily realized R
- daily risk capacity
- max concurrent positions
- daily profit/loss guard
- TP/BE state
- re-entry state
- equity curve
- drawdown

Market ticks are not reread 15 times.

## 5.3 Historical test ranges

### Experimental range
`2026-01-01 → current test date (2026-09-28 for the initial roadmap baseline)`

This phase is used to finalize the strategy/rule set before the extended historical test.

### Extended historical development range
`2020-07-01 → 2026-09-28`

But the entire calendar year:

`2025-01-01 → 2025-12-31`

is excluded from all development/optimization/rule-selection processing and is reserved strictly for OOS.

Therefore the development data comprises:
- 2020-07-01 → 2024-12-31
- 2026-01-01 → 2026-09-28

and 2025 remains untouched until the final OOS run.

## 5.4 Report hierarchy
For every tested period:

### Monthly
For each month display at minimum:
- Year
- Month
- Total trades
- TP count
- SL count
- BE count
- Guard-blocked/guard-stopped count where applicable
- Net R
- Gross R
- Max Drawdown R
- Max Drawdown Touch Count
- Maximum consecutive losses
- Maximum consecutive wins
- Additional execution-cost metrics required by the trade ledger

### Annual
After all months of a year:
- the exact same metric family aggregated for the full year.

### Grand Total
For a multi-year run:
- the same metric family aggregated over the entire tested development/OOS span as requested.

## 5.5 Max Drawdown and Touch Count

Drawdown is calculated from the net equity curve in R using realized/cost-adjusted results and the applicable position state.

For each report period:
- `MaxDD_R` = deepest peak-to-trough drawdown inside that period.
- `MaxDD_TouchCount` = number of distinct returns of the equity curve into the maximum-drawdown zone for that period.

The implementation must use a deterministic tolerance input so floating-point noise does not create false separate touches.

A practical default is:
- `DDTouchToleranceR = 0.05R`

A new touch is counted only after the curve has first exited that tolerance band and later re-entered it.

This metric must be calculated independently for every month, every year and the full requested period.

Example:
- 2026 MaxDD = 8.4R
- MaxDD Touches = 5

means the year's equity curve revisited the 8.4R drawdown zone five distinct times; the example value is illustrative only.

## 5.6 Output artifacts
The research run must produce machine-readable and human-readable results sufficient to reproduce the reports without rerunning the strategy.

Recommended core artifacts:
- Trade Ledger
- Scenario Summary
- Monthly Report
- Annual Report
- Grand Total Report
- Validation/diagnostic log

# Phase 6 — Validation, Freeze, Extended Test & Final OOS

### Goal
Prove the engine is deterministic and that research results are not being distorted by execution, look-ahead, reporting or risk-accounting errors.

## 6.1 Deterministic validation
Validate at minimum:
- zero look-ahead
- exact signal-candle close → next-tick execution
- exact Bid/Ask usage
- spread captured at the event tick
- no forced exit from floating DD alone
- max 3 concurrent positions
- daily risk admission correctly reserves open-trade worst-case risk
- daily guard blocks new positions at remaining capacity limit
- daily profit target blocks new positions when enabled
- no post-TP/BE re-entry under the same setup
- re-entry counts obey 1/2/3/4 attempts
- no duplicate setup from clustered liquidity levels
- correct month/year assignment using broker server time
- monthly/yearly reports sum from one ledger and do not rerun the engine
- Matrix results are isolated per scenario.

## 6.2 Result freeze after experimental range
Only after the `2026-01-01 → 2026-09-28` experimental work is finalized are rules/filters/parameters frozen for the extended research run.

No strategy rule may be changed to improve the extended historical result after observing that result.

## 6.3 Extended development test
Run the frozen strategy over:
- 2020-07-01 → 2024-12-31
- 2026-01-01 → 2026-09-28

Do not include 2025.

## 6.4 Final OOS test
Run the frozen strategy once on:

`2025-01-01 → 2025-12-31`

No rule selection, optimization or filter approval may use the OOS result.

## 6.5 Research conclusion package
Final package must contain:
- code state used for the final run
- exact Inputs/configuration
- compile/test logs
- experimental report
- extended development report
- 2025 OOS report
- full-period aggregation
- explanation of any data gaps or tester limitations
- updated roadmap showing all completed phases

# Final Definition of Done

The project is considered complete only when all of the following are true:

- Core liquidity sources are deterministic and selectable.
- Sweep, Entry, SL, TP and BE rules are unambiguous.
- M1 is the default and timeframe is configurable.
- Broker/server time is authoritative.
- All three trading-session modes work.
- Real tick Bid/Ask and instantaneous spread are used for execution.
- Costs are tracked from the beginning.
- Risk is dynamic in R and the daily 3R guard is configurable and enabled by default.
- Maximum concurrent positions defaults to 3 and is configurable.
- Floating drawdown never force-closes a trade solely because it approaches the daily limit.
- Daily profit target is available at 9R but disabled by default.
- Single-TP and 15-scenario TP/BE matrix modes both work.
- Re-entry limit is configurable from 1–4 attempts and defaults to one attempt.
- The three strategy-specific filters exist, are independently switchable, and are OFF by default.
- One market-data pass can generate the full research ledger and all monthly/yearly/full-period reports.
- Monthly, annual and grand-total reports include MaxDD and MaxDD Touch Count.
- 2025 remains a clean OOS year in the extended research design.
- Every code-changing phase updates this roadmap and outputs the updated roadmap plus changed files under unchanged filenames/paths.
